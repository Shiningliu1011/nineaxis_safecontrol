# 状态流与指令流 QoS 时延验证（2026-09-23）

## 测量方法

`scripts/measure_qos_latency.py` 启动独立的 ROS 2 控制器与被控对象进程，运行实际
`OscbfController`、JAX 控制计算和 `OscbfPlant` 仿真。被控对象发送状态、控制器状态
订阅回调收到状态、控制器完成计算并准备发布指令、被控对象收到指令时，分别记录
同一主机的 `time.monotonic_ns()`。状态和指令的 `header.stamp` 用于关联消息；三段
时延均由单调时钟计算。状态未到达数量由状态发送与订阅回调的消息身份直接比较。

每组预热 2 秒、测量 20 秒、控制器设定频率 100 Hz，使用相同初始位姿和轨迹，各组使用
独立 `ROS_DOMAIN_ID`。状态发布端保持 depth 20；状态订阅端和指令发布、订阅两端
分别比较 depth 5/20，第二轮反转组合顺序。结束前 100 ms 发出的状态不进入接收率
计算，以留出消息传输时间。已到达但未形成独立指令的状态单独计数，不能直接判定为
DDS 丢包。实际指令发布数量随运行时计算和调度变化，逐组列出。时延样本必须关联
状态发送、控制器完成、指令到达三个事件，并满足时间顺序。

环境：ROS 2 Humble、`rmw_fastrtps_cpp`、Linux x86_64、Intel Core i7-11800H、
Python 3.10.12、JAX CPU。测量时 `HEAD` 为
`b7f904b8c3933f1e7bc710dcafb31169262f29c8`，工作区包含本票改动。三次测量的
`summary.json` 均记录运行时生效的源码和配置 SHA-256；其中测量脚本为
`b9655a88d59b530ce72bf022005e312b8e44dc88c1be0559abfbb93d88dff871`，
`ros_conventions.py` 为
`0b388d63a942d7fcd7b81015791729f4a95eb541d4af835dfd807960b1c05c69`，
`oscbf_controller.py` 为
`8e4f64a9afe83ba884bfbecdbce2b0a93b3137df39676dfdd7a5d144bcb05b32`，

`a92f8e4af2fadf9b176398520ba7c265db91be1452a93c26ecc2337dc0ef7de2`。

运行命令（先加载 ROS 2 Humble 与工作区环境）：

```bash
python3 scripts/measure_qos_latency.py --base-domain 180
python3 scripts/measure_qos_latency.py --reverse --base-domain 200
python3 scripts/measure_qos_latency.py --production-qos --state-depths 20 --command-depths 5 --base-domain 220
```

八组的状态未到达数均为 0；状态订阅 depth 5 和 20 在这两轮运行中没有接收率差异。
同一组合的完整链路 p99 随运行轮次变化，不能据此推断某个 depth 稳定降低总时延。
两种指令 depth 均出现过单条指令缺少到达记录，depth 20 未显示可重复的传输收益。
状态流保持现有 depth 20；指令流采用 depth 5，以减少排队等待的旧指令。两条流
分别采用 KEEP_LAST / BEST_EFFORT / VOLATILE。本机仿真数据不能用作真机时延保证。

# 通用能力优先复用上游框架

项目已有较多本地控制、感知和规划实现，继续扩展会增加与上游重复维护的成本。用户明确要求：已有成熟开源框架应直接复用，必要时在其基础上修改完善。因此采用复用优先的架构方向；具体包、版本、接口和替换顺序仍由[复用优先地图](../planning/oscbf-reuse/MAP.md)中的决策票确定，本记录不批准任何尚未选定的替换方案。

优先评估直接依赖；不能覆盖项目需求时，记录缺口，再比较适配、上游补丁和必要的项目扩展。已有本地实现的存在本身不构成继续自研的理由；上游有演示也不构成本项目可直接采用的证据。

用户后续明确以实际效果择优保留，详见[边界补充决议](../planning/oscbf-reuse/issues/03-reuse-boundary.md#用户补充决议按实际效果择优保留待发布)。复用优先表示优先评估成熟上游；已有实现具有比较优势时可以保留，替换应有满足验证要求且收益明确的证据。控制接入阶段曾决定保留自碰撞 OBB；该项已由 [ADR 0010](0010-unified-scale-collision-safety-module.md) 替代。

自研规划器不再使用 MoveIt/OMPL 运行路径，AEB-RRT* 研究方法与 JAX trajectory
optimization 的组合见 [ADR 0024](0024-aeb-rrtstar-with-jax-trajectory-optimization.md)。

## 取舍与后果

相比继续掌控全部实现，复用减少通用能力的维护范围，但引入上游版本、许可证和升级兼容性的约束。九轴机器人及任务需求不能为迁就上游演示而默默改变；退役旧实现前需要对应验证证据。各框架的最终选型和实际补丁范围仍待后续决策。

## 已确认的研究与维护边界

2026-09-07 用户已确认[独有能力与上游维护边界决议](../planning/oscbf-reuse/issues/03-reuse-boundary.md)。这使复用路线必须兼容保留的研究插件，同时允许承担有明确范围的上游补丁维护成本；不能以复用为由取消研究成果，也不能把补丁许可解释为重建通用框架。具体批准内容与对话依据以该决策票为准。
